# `firm-db` — Package Planning Document

**Drizzle ORM · PostgreSQL · Supabase · RLS Tenant Isolation · Connection Factories · Structural Query Helpers · Schema Versioning**

---

## 0. Purpose & Architectural Position

`firm-db` is the **single source of truth for all database schema definitions, connection management, and structural query helpers** in the platform. It contains Drizzle ORM table definitions, migration files, RLS tenant isolation enforcement, and typed query factories — **no business logic, no feature-specific queries**.

**Layer placement:** Layer 2, Wave 3 — built fourth, after `firm-api-contracts`. It depends on `firm-types` (branded IDs, entity interfaces) and `firm-validators` (canonical Zod schemas for runtime validation of database inputs/outputs).

**What it owns:**

| Domain | Mechanism |
|---|---|
| Table definitions | Drizzle ORM schema files — the structural shape of every table |
| Tenant isolation | RLS policy definitions + `setTenantContext()` runtime enforcement |
| Connection management | Factory functions for serverless, pooled, and direct connection modes |
| Query helpers | Typed wrappers: `paginate()`, `softDelete()`, `withTenant()`, `auditTrail()` |
| Migrations | Drizzle Kit migration files — version-controlled, never edited after deployment |
| Seed data | Development and CI seed scripts — deterministic, idempotent |

**2026 context:** Drizzle ORM is at v1.0+ (stable, with `drizzle-kit` v1.0 for migration management). PostgreSQL 17 is the current stable release (September 2024), with PG18 expected Q3 2026. Supabase is the platform's managed PostgreSQL provider, offering native RLS, connection pooling via PgBouncer, and branching for preview environments. `postgres.js` is the canonical TypeScript client for PostgreSQL.

## 1. Immutable Rules

| Rule | Rationale |
|---|---|
| **No business logic.** Table definitions, connection factories, structural helpers only. Feature-specific queries live in feature packages (Layer 6). | Single responsibility — schema ownership stays here; query logic is a feature concern. |
| **Every shared-schema table ships with its RLS policy and test in the same PR.** | RLS is structural, not advisory. A table without RLS is a data leak waiting to happen. CI blocks PRs that add tables without corresponding RLS. |
| **Every database query runs inside `setTenantContext()`.** Sets `app.current_tenant_id` for RLS enforcement. No query bypasses tenant context — not even internal tools. | Tenant isolation is enforced at the database level, not application level. `tenantId` is a session variable, not a WHERE clause. |
| **Connection mode is always explicit.** `serverless`, `pooled`, or `direct` — never inferred from environment. | Prevents silent connection pooling mismatches. Serverless environments (Vercel, Lambda) need different connection strategies than long-running workers. |
| **No raw SQL in feature packages.** All database access goes through Drizzle's typed query builder or structural helpers defined here. | Raw SQL bypasses type safety, RLS, and brand enforcement. The only exceptions are migration files (generated by `drizzle-kit`) and seed scripts (explicitly exempted). |
| **Branded IDs are preserved in database types.** Column types use `varchar` with branded type annotations — `TenantId`, `UserId`, `LeadId` are never plain `string`. | Prevents ID mix-ups at the database layer. Drizzle's custom type system supports branded columns. |
| **Schema versioning starts at the first breaking change.** Migration files are sequential. Downgraded migrations are never deleted — they remain in the migration directory for auditability. | Every deployed migration is immutable. Roll-forward fixes, never roll-back. |
| **`exports` field is the contract boundary.** Only `src/index.ts` reachable from outside. Internal schema files are invisible to consumers. | Feature packages import from `firm-db`, not from `firm-db/src/schemas/leads.ts`. |
| **Connection strings come exclusively from `firm-env` validated environment variables.** No hardcoded URLs, no fallback defaults. | Secret management is a Layer 1 concern. This package consumes validated env vars only. |
| **Named exports only.** No default exports. | Consistent import patterns. |

## 2. RLS Tenant Isolation Architecture

### 2.1 The Core Mechanism

Every table that contains tenant-scoped data includes a `tenant_id` column typed as `TenantId`. Row-Level Security (RLS) policies ensure that queries can only access rows where `tenant_id = current_setting('app.current_tenant_id')::uuid`:

```sql
-- Generated policy for every shared-schema table
ALTER TABLE leads ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Tenant isolation for leads"
  ON leads
  FOR ALL
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

`setTenantContext()` sets the session variable before every query:

```typescript
// packages/firm-db/src/connection/tenant-context.ts
export async function setTenantContext(
  tenantId: TenantId,
  db: DrizzleDB
): Promise<void> {
  await db.execute(sql`SET LOCAL app.current_tenant_id = ${tenantId}`);
}
```

**Why `SET LOCAL`?** The setting is scoped to the current transaction. If the caller forgets to call `setTenantContext()`, query fails because `current_setting('app.current_tenant_id')` raises an error — rather than silently returning zero rows.

### 2.2 Tables That Skip RLS

Some tables are **platform-level**, not tenant-scoped, and explicitly skip RLS:

| Table | Reason |
|---|---|
| `tenants` | The tenant registry itself — queried during tenant resolution, before tenant context is set |
| `users` | Users can belong to multiple tenants; tenant association is via a join table |
| `migrations` | Drizzle Kit migration tracking — no business data |
| `feature_flags` | Platform-level flags — evaluated before tenant context exists |

Every RLS exemption must be documented in a comment on the table definition and reviewed in the same PR that adds the table. CI checks that every table without an `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` statement has a documented exemption reason.

### 2.3 `CrossTenantAccessError`

Any attempt to access a row outside the current tenant context returns zero rows (RLS silently filters). The application layer **never** catches this case by checking row counts — it would reveal tenant existence. Instead, `CrossTenantAccessError` is a 403, never a 404.

## 3. Connection Management

### 3.1 Connection Modes

| Mode | Use Case | Pool Implementation | Max Connections |
|---|---|---|---|
| **serverless** | Vercel Edge Functions, Lambda handlers | Supavisor (Supabase's managed pooler) via `postgres.js` with `max: 1` | 1 per invocation |
| **pooled** | Long-running services, Inngest workers | PgBouncer (Supabase) or internal pool via `postgres.js` with `max: 20` | 20 per service instance |
| **direct** | Migrations, seed scripts, CI | Direct PostgreSQL connection — no pooler | 1 per CLI invocation |

Connection factories are explicit:

```typescript
// packages/firm-db/src/connection/factories.ts
import { createClient, type Client } from 'firm-db';

// Serverless — one-shot connections
export function createServerlessClient(): Client { /* ... */ }

// Pooled — for workers and services
export function createPooledClient(): Client { /* ... */ }

// Direct — for migrations and seeds
export function createDirectClient(connectionString: string): Client { /* ... */ }
```

**Never inferred:** Each factory is called explicitly. The caller chooses the mode based on the runtime environment. `NODE_ENV` is not used to determine pool size.

### 3.2 `postgres.js` as the Underlying Driver

Drizzle ORM uses `postgres.js` (`postgres` npm package v4+) as its PostgreSQL driver. This is the recommended driver for Drizzle in 2026 — it supports:

- Async/await query interface
- Connection pooling with prepared statement caching
- Logical replication listeners (for cache invalidation)
- Supabase-compatible authentication via connection string

```typescript
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';

const client = postgres(env.DATABASE_URL, {
  max: 20,                  // pooled mode
  idle_timeout: 30,         // 30s idle timeout
  connect_timeout: 10,      // 10s connection timeout
  prepare: true,            // cache prepared statements
});

export const db = drizzle(client, { schema });
```

### 3.3 Connection Validation

Before any query, the connection factory validates:

1. The connection string is a valid PostgreSQL URL.
2. SSL is enforced (`sslmode=require` in connection string or equivalent).
3. The server version is ≥ PostgreSQL 17.
4. The database exists and is accessible.

Validation failures throw `DatabaseConnectionError` (a typed error from `firm-errors`) — the application refuses to start with a broken database connection.

### 4.2 Table Definition Pattern

Every table follows a consistent structure:

```typescript
// packages/firm-db/src/schemas/leads.ts
import { pgTable, uuid, varchar, timestamp, text, jsonb } from 'drizzle-orm/pg-core';
import { sql } from 'drizzle-orm';
import { createTenantId, createLeadId, createUserId } from 'firm-types';
import { tenants } from './tenants';
import { users } from './users';

export const leads = pgTable('leads', {
  // ── Primary key ──
  id:        uuid('id').primaryKey().defaultRandom().$type<LeadId>(),

  // ── Tenant isolation ──
  tenantId:  uuid('tenant_id').references(() => tenants.id).notNull().$type<TenantId>(),

  // ── Business fields ──
  email:     varchar('email', { length: 254 }).notNull(),
  firstName: varchar('first_name', { length: 200 }).notNull(),
  lastName:  varchar('last_name', { length: 200 }).notNull(),
  phone:     varchar('phone', { length: 30 }),
  source:    varchar('source', { length: 50 }).notNull().default('website'),
  status:    varchar('status', { length: 50 }).notNull().default('new'),

  // ── Metadata ──
  metadata:  jsonb('metadata').default(sql`'{}'::jsonb`),

  // ── Ownership ──
  assignedTo: uuid('assigned_to').references(() => users.id).$type<UserId>(),

  // ── Timestamps ──
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
  updatedAt: timestamp('updated_at', { withTimezone: true }).defaultNow().notNull(),
  deletedAt: timestamp('deleted_at', { withTimezone: true }),

  // ── Constraints ──
}, (table) => ({
  // Index for tenant-scoped queries
  tenantIdx:         sql`CREATE INDEX idx_leads_tenant_id ON ${table} (tenant_id)`,
  // Unique constraint: one email per tenant
  uniqueEmailPerTenant: sql`CREATE UNIQUE INDEX idx_leads_tenant_email ON ${table} (tenant_id, email) WHERE deleted_at IS NULL`,
}));
```

**Key conventions:**
- `$type<LeadId>()` brands the column at the TypeScript level.
- Indexes are defined as table constraints, not raw SQL in migration files.
- Soft-delete is supported via `deleted_at` with partial unique indexes.
- `tenantId` is always the second column — consistent across all tables.

### 4.3 Relations

Drizzle relations are defined in a separate `relations.ts` file per schema domain, imported and re-exported from `schemas/index.ts`:

```typescript
// packages/firm-db/src/schemas/relations/leads.ts
import { relations } from 'drizzle-orm';
import { leads } from '../leads';
import { tenants } from '../tenants';
import { users } from '../users';

export const leadsRelations = relations(leads, ({ one }) => ({
  tenant:  one(tenants, { fields: [leads.tenantId], references: [tenants.id] }),
  assigned: one(users,   { fields: [leads.assignedTo], references: [users.id] }),
}));
```

## 5. Structural Query Helpers

### 5.1 `paginate()` — Cursor-Based Pagination

Cursor-based pagination is the default for all list endpoints. Offset-based is available for admin dashboards requiring jump-to-page navigation.

```typescript
// packages/firm-db/src/helpers/paginate.ts
import type { PgTable, PgColumn } from 'drizzle-orm/pg-core';
import { and, gt, lt, asc, desc } from 'drizzle-orm';
import type { TenantScopedDB } from '../connection/tenant-context';

interface CursorPaginateOptions<T extends PgTable> {
  table: T;
  cursorColumn: PgColumn;           // Usually 'id' or 'created_at'
  cursor?: string;                   // Base64-encoded cursor value
  limit?: number;                    // Default 50, max 100
  order?: 'asc' | 'desc';           // Default 'desc' (newest first)
}

interface CursorPaginateResult<T> {
  data: T[];
  nextCursor: string | null;        // Base64-encoded next cursor, null if last page
  hasMore: boolean;
}

export async function cursorPaginate<T extends PgTable>(
  db: TenantScopedDB,
  options: CursorPaginateOptions<T>,
): Promise<CursorPaginateResult<T>> { /* ... */ }
```

### 5.2 `softDelete()` — Soft Deletion with RLS

Sets `deleted_at = NOW()` and ensures the row belongs to the current tenant:

```typescript
export async function softDelete<T extends PgTable>(
  db: TenantScopedDB,
  table: T,
  id: BrandedId,
): Promise<void> {
  // RLS ensures tenant ownership — only sets deleted_at, never physically removes
  await db
    .update(table)
    .set({ deletedAt: new Date() })
    .where(eq(table.id, id))
    .execute();
}
```

### 5.3 `createAuditEntry()` — Immutable Audit Log

Every privileged action writes an immutable audit record:

```typescript
export async function createAuditEntry(
  db: TenantScopedDB,
  entry: {
    tenantId: TenantId;
    userId: UserId;
    action: string;
    resource: string;
    resourceId: string;
    changes?: Record<string, unknown>;
  },
): Promise<void> {
  await db.insert(auditLogs).values({
    ...entry,
    id: crypto.randomUUID(),
    timestamp: new Date(),
  }).execute();
}
```

The `audit_logs` table has a `SELECT`-only RLS policy — no updates, no deletes.

## 6. Migration Strategy

### 6.1 Generation

Migrations are generated by Drizzle Kit:

```bash
pnpm drizzle-kit generate
```

This compares the current schema definitions against the migration history and produces a new SQL file in `drizzle/migrations/`. Generated files are committed to version control and **never edited manually**.

### 6.2 Application at Startup

During application startup (`instrumentation.ts` in Next.js 16, or service entry point for workers), pending migrations are applied:

```typescript
// packages/firm-db/src/migrations.ts
import { migrate } from 'drizzle-orm/postgres-js/migrator';
import { createDirectClient } from './connection/factories';

export async function applyMigrations(databaseUrl: string): Promise<void> {
  const client = createDirectClient(databaseUrl);
  await migrate(client, { migrationsFolder: './drizzle/migrations' });
  await client.end();
}
```

**Important:** Migrations run with a **direct** connection — pooled connections may conflict with DDL statements. Never run migrations through Supavisor or PgBouncer.

### 6.3 Rollback Policy

Downgrading is architecturally prohibited. Every migration is forward-only. If a migration introduces a bug:

1. Write a **new** migration that fixes the issue.
2. Never delete or modify an existing migration file.

This guarantees that every deployed database can reconstruct its schema history from the migration directory.

### 6.4 CI Validation

| Gate | Command | What It Enforces |
|---|---|---|
| **Migration freshness** | `drizzle-kit check` | Schema definitions match the latest migration |
| **Migration idempotency** | Apply migrations to a fresh test database, then re-apply | Second run is a no-op |
| **RLS coverage** | Script `scripts/check-rls.ts` parses migration SQL for `ENABLE ROW LEVEL SECURITY` | Every table has RLS enabled or a documented exemption |
| **No manual edits** | CI checks migration files are identical to `drizzle-kit generate` output | Generated files are never manually modified |

## 8. Test Strategy

### 8.1 RLS Tests (Per Table)

Every shared-schema table must have an RLS test that verifies:

1. **Tenant A can read and write its own rows.**
2. **Tenant A cannot read or write Tenant B's rows.**
3. **Query without `setTenantContext()` throws an error.**
4. **Platform-level tables (tenants, users) are accessible before tenant context is set.**

```typescript
// tests/rls/leads.test.ts
import { describe, it, expect, beforeAll, afterAll } from 'vitest';
import { createDirectClient, setTenantContext } from 'firm-db';
import { leads } from 'firm-db';
import { asTenantId, asLeadId } from 'firm-types';

describe('RLS: leads', () => {
  const db = createDirectClient(process.env.DATABASE_URL!);

  it('allows tenant A to insert a lead', async () => {
    await db.transaction(async (tx) => {
      await setTenantContext(TENANT_A, tx);
      const result = await db.insert(leads).values({ /* ... */ }).returning();
      expect(result[0].tenantId).toBe(TENANT_A);
    });
  });

  it('prevents tenant A from reading tenant B leads', async () => {
    await db.transaction(async (tx) => {
      await setTenantContext(TENANT_A, tx);
      const results = await db.select().from(leads).execute();
      expect(results.every(r => r.tenantId === TENANT_A)).toBe(true);
    });
  });

  it('throws when tenant context is not set', async () => {
    await expect(
      db.select().from(leads).execute(),
    ).rejects.toThrow();
  });
});
```

### 8.2 CI Test Environment

Tests run against a **real PostgreSQL instance** — never SQLite or an in-memory mock. RLS tests require a real database because RLS behavior cannot be mocked.

CI uses Supabase branching to create a temporary database for each PR. The seed script creates the test tenants and applies all migrations. Tests run, and the branch is destroyed after CI completes.

### 8.3 Testing `$type<>()` Branded Columns

Drizzle's `$type<>()` is a compile-time annotation only — it does not enforce brands at runtime. The test suite verifies that:

1. The TypeScript compiler rejects assignments of `string` to `$type<LeadId>()`.
2. Zod validation (in `firm-validators`) catches invalid formats at runtime.
3. The database's `uuid` type rejects non-UUID values.

## 10. Consumer Patterns (Quick Reference)

### 10.1 For feature packages (Layer 6)

```typescript
// packages/firm-feature-crm/src/lead-service.ts
import { db, leads, setTenantContext, cursorPaginate } from 'firm-db';
import type { TenantScopedDB } from 'firm-db';
import { leadSchemaV2 } from 'firm-validators';

export async function getLeads(tenantId: TenantId, cursor?: string) {
  return db.transaction(async (tx) => {
    await setTenantContext(tenantId, tx);
    return cursorPaginate(db, {
      table: leads,
      cursorColumn: leads.createdAt,
      cursor,
      limit: 20,
    });
  });
}

export async function createLead(tenantId: TenantId, input: unknown) {
  // Validate at the API boundary
  const validated = leadSchemaV2.parse(input);

  return db.transaction(async (tx) => {
    await setTenantContext(tenantId, tx);
    const [lead] = await db
      .insert(leads)
      .values({
        ...validated,
        tenantId, // RLS ensures this matches the current context
      })
      .returning();

    return lead;
  });
}
```

## 11. Interface Freeze & Governance

- After Wave 3, table schemas are governed by the Schema Versioning policy: adding nullable columns is backward-compatible (minor); renaming or removing columns requires a new migration and is a major change.
- Any PR that adds a new table **without** `ENABLE ROW LEVEL SECURITY` is rejected by CI.
- Any PR that modifies a table schema **without** a corresponding migration is rejected by `drizzle-kit check`.
- `setTenantContext()` is the only path to set tenant context for database queries. Direct calls to `db.query.leads.findMany()` without tenant context fail at the database level — but CI also scans for unprotected queries.
- Migration files are immutable after merge to `main`. Cherry-picking migration fixes across branches is prohibited.
