# Internationalization – How We Handle i18n in This Monorepo

This guide covers our i18n strategy, library, routing, message management, and RTL support. For library comparisons, see the archived research.

---

## 1. Library: next-intl

We use **next-intl** (≥4.9.2) for all Next.js applications. It is built for the App Router, supports Server Components natively, and uses ICU MessageFormat.

**Security note:** Versions prior to 4.9.2 have a prototype pollution vulnerability (SNYK‑JS‑NEXTINTL‑16438971). Only applies if `experimental.messages` + `messages.precompile: true` are enabled.

---

## 2. Locale Routing

We use **subdirectory routing** (`/en/about`, `/es/about`). This is Google‑recommended and ensures CDN independence.

The i18n middleware (created via `createMiddleware()` from `next-intl`) performs:

1. **Detection** – reads `accept-language` header.
2. **Cookie check** – previously selected language takes priority.
3. **Redirect** – if URL lacks a locale prefix, redirect to detected locale.
4. **Validation** – if locale is not supported, redirect to default.

Configuration uses `localePrefix: 'always'` so each locale variant is a distinct CDN cache entry.

---

## 3. Shared Package (`@firm/i18n`)

### Structure
```
packages/i18n/
├── messages/
│   ├── en/ (common.json, forms.json, errors.json, seo.json, navigation.json)
│   ├── es/ (same structure)
│   └── fr/ (same structure)
├── middleware.ts   ← createMiddleware() wrapper
├── navigation.ts   ← typed Link & useRouter replacements
└── index.ts
```

### Translation Sync Pipeline

- **Automated Pull**: GitHub Action pulls translations from Crowdin/Lokalise daily
- **PR Creation**: Opens PR with updated JSON files for each locale
- **CI Validation**: Ensures 100% translation completeness before merge
- **Branch Strategy**: Separate branches per locale (`i18n/fr`, `i18n/es`) to enable parallel reviews
- **Manual Updates**: Direct commits to translation files for urgent fixes
- **Fallback Plan**: If translation service is unavailable, use polyfill in worklet or remain on `Date` until Baseline 2027
Each client app can extend or override any namespace. The base messages in `@firm/i18n` provide agency defaults; client apps merge their own translations on top.

---

## 4. Message Management

- Keys use namespaced dot notation: `forms.contact.name.label`, `errors.validation.required`.
- ICU MessageFormat for pluralization, gender, and dynamic values.
- `useExtracted` (experimental) auto‑extracts inline messages during `next dev` and `next build`. CI checks that all configured locales have complete key coverage.
- Translations are managed via a translation platform (Crowdin / Lokalise), synced back to JSON files in the monorepo.

---

## 5. Date, Number & Currency Formatting

We use the browser’s built‑in **`Intl` API** for all locale‑specific formatting:

```typescript
new Intl.DateTimeFormat(locale).format(date)
new Intl.NumberFormat(locale, { style: 'currency', currency: 'USD' }).format(amount)
new Intl.RelativeTimeFormat(locale).format(-1, 'day')
new Intl.DurationFormat(locale).format({ hours: 2, minutes: 30 })
```

**Temporal Support:**
- `Intl.DateTimeFormat` now accepts `Temporal.PlainDateTime` objects (modern browsers)
- **Fallback**: Use standard `Date` objects until Temporal reaches Baseline 2027 support
- **Production Baseline**: Continue with `Date` objects for compatibility with existing browser support

---

## 6. RTL (Right‑to‑Left) Support

We use Tailwind CSS v4.2 **logical properties** to build LTR/RTL compatible layouts from a single source:

| LTR‑specific (avoid) | RTL‑specific (use) |
|----------------------|-------------------|
| `ml-4`, `mr-4`       | `ms-4`, `me-4` |
| `pl-4`, `pr-4`       | `ps-4`, `pe-4` |
| `text-left`, `text-right` | `text-start`, `text-end` |
| `left-0`, `right-0`    | `inset-inline-s-0`, `inset-inline-e-0` |
| `object-left`, `object-right` | `object-top`, `object-bottom` |

**shadcn/ui RTL Migration:**
- The `pnpm dlx shadcn@latest migrate rtl` command converts existing components to use logical properties.
- **New RTL projects** use the `--rtl` flag to enable RTL-specific defaults.

**HTML Direction:**
- The `<html>` element must have `dir="rtl"` and `lang="ar"` set for RTL layouts.
- **Component Testing:** Playwright visual tests compare LTR and RTL screenshots to detect layout breaks.

---

## 7. SEO Implications

- **Hreflang tags** are auto‑generated by `@firm/seo` for every page, with bidirectional validation in CI.
- Sitemap‑based hreflang (`xhtml:link` elements) is used for large sites.
- Each locale variant has a **self‑referencing canonical URL**.
- LLMs (ChatGPT, Perplexity) expect translated structured semantic content — not just visual translation.

# Testing & Quality Assurance – How We Test in This Monorepo

This guide covers our test pyramid, tools, selective execution strategy, and quality gates. For tool comparisons, see the archived research.

---

## 1. Test Pyramid

| Layer | Tool | Scope | Target Coverage |
|-------|------|-------|-----------------|
| **Unit** | Vitest 4.1+ | Pure logic in shared packages | ≥80% shared packages; ≥70% apps |
| **Integration** | Vitest + Supertest | Package interactions, DB queries | Key service boundaries |
| **E2E** | Playwright 1.59 | Critical user journeys | 3–5 core flows per client app |
| **Visual Regression** | Storybook 10.3 + Chromatic | UI components across all themes | All `@firm/ui` components |
| **Accessibility** | axe‑core (integrated in Playwright & Storybook) | All rendered pages | Zero critical/serious WCAG 2.2 AA violations |

**Selective execution** via Turborepo ensures only affected tests run on each PR.

---

## 2. Unit & Integration Tests: Vitest 4.1

### Key Features We Use
- **Test Tags** – organize tests into groups (e.g., `db`, `flaky`) with shared options like timeout and retries.
- **Workspace Mode** – shared configuration, per‑package overrides, parallel execution.
- **AI Agent Reporter** – reduces token usage when running inside AI coding agents.
- **`aroundEach`/`aroundAll`** – wrap tests in database transactions or tracing spans.

### Database Testing
We use **PGlite** (WASM PostgreSQL, <3MB) for real PostgreSQL tests in milliseconds, without Docker. Each test gets a pristine database. Supports pgvector.

### API Testing
**Supertest** against the running application. Assertions include status codes, response shape (validated against Zod schemas), and tenant isolation (cross‑tenant requests must return 403).

---

## 3. E2E Tests: Playwright 1.59

### Core Flows (per client app)
1. Homepage load – 200, no console errors, LCP under budget.
2. Contact form – fill, submit, success message, lead appears in CRM.
3. Blog navigation – homepage → blog index → individual post → related posts.
4. Authenticated flow (portal) – login → dashboard → view analytics → logout.

Tests run against the preview URL deployed by CI. Traces and videos are recorded on failure.

### AI Ecosystem
Playwright 1.59 provides MCP, built‑in agents (Planner, Generator, Healer), and accessibility‑tree‑first execution. The **Healer agent** auto‑patches selectors when tests fail due to DOM changes.

---

## 4. Visual Regression: Storybook 10.3 + Chromatic

- Every `@firm/ui` component has a Storybook story.
- SteadySnap reduces visual inconsistencies by 34% (freezes animations, GIFs, CSS transitions).
- **Multi‑theme testing:** Every story is rendered in all configured client themes (`data‑theme="acme"`, `"belmont"`). Chromatic snapshots all variants in one CI run.
- Budget: full snapshot suite only on merge to `main`; affected stories only on PR branches.

---

## 5. Accessibility Testing

- **axe‑core** integrated in both Playwright (`@axe-core/playwright`) and Storybook (built‑in addon).
- **Zero critical or serious violations** allowed on any new or modified page.
- CI blocks merge on violations.
- Manual testing with assistive technologies (keyboard, VoiceOver, NVDA) is part of the launch checklist.

---

## 6. Contract Testing

When services communicate through shared Zod schemas in `@firm/api-contracts`, contract tests verify both sides honor the schema.

- Consumers generate tests from the published schemas.
- CI runs contract tests for all dependent consumers when the API schema changes, catching breaking changes before deployment.
- Pact‑style consumer‑driven contracts are used for public REST APIs.

---

## 7. Tenant Isolation Tests

A dedicated test suite verifies multi‑tenant boundaries:

- Authenticate as Tenant A, attempt access to Tenant B’s resource → 403 or empty result.
- Run on every PR that modifies auth, database, analytics, or caching logic.

---

## 8. Flaky Test Management

- Flaky tests are tagged with `{ name: 'flaky', retry: 3 }` in Vitest.
- The `github-actions` reporter highlights flaky tests in CI summaries.
- Quarantined tests don’t block the build but are tracked in a weekly “test health” report.
- Tests older than 30 days without a fix are deleted.
